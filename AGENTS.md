# AGENTS.md

Rules for any agent or contributor changing this repo. README.md has the detail; this file is the short list of what must not break and how to check a change.

## What this is

A fan site (https://depauwvswabash.com/) comparing DePauw University and Wabash College: all-time head-to-head athletics records, merged from both schools' own history pages by a scraper that runs on GitHub Actions, plus a hand-curated alumni and endowment page. `scraper/render.py` writes static HTML. Unofficial; not affiliated with either school.

Read the README sections you touch: "How the data updates", "Reading and adjusting the logic", "Review hold", "Snapshots and archiving", "Adding a sport", "Data format", "Contributing", and "Where things are" (the file map).

## Before you call a change done

Commands are in README "Run it locally". Run them from the repo root. The bot-managed data files are not on `main`: run `python scraper/databranch.py fetch` first (and `python scraper/scrape.py --remerge-only` if you changed `overrides.json` or the merge code), or `pytest` and `render.py` stop and say so.

1. `python -m pytest -q tests`
2. `python scraper/render.py`
3. `node --check static/easter-eggs.js`, then html-validate on all ten built pages (`npm ci --ignore-scripts` once, then the commands in README and `.github/workflows/checks.yml`).
4. The Mermaid diagram check (same two places). GitHub draws with a newer Mermaid than the CLI, so after a diagram change also look at the README on GitHub.
5. Visible change: look at the result at 375px wide and at desktop width, in light and dark mode, and show it. Also go through it with the keyboard alone, at 320px wide and at 200% zoom, and run `node axe/run.js` (README "Run it locally"; the `axe` job in `checks.yml` runs the same script on the pull request).
6. Update the README in the same PR. A change to the pipeline, data files, workflows, triggers or game-day behavior also updates the matching README diagram (and the workflow table). Keep the how-it-works text, module docstrings, workflow comments, issue templates and `scraper/sources.json` `_comment` in step with the code.
7. Tests gate every deploy: a failing test stops all updates (scheduled, push and manual). Never write a test that depends on today's date, the current season or a live page.
8. Tests must never read the real clock, the network, or the bot-updated files in `data/` for an exact number. Pass a fixed `now` and use `tests/fixtures/` (the frozen `series-frozen-2026-10-30.json` for exact counts); checks on the live data are rules that always hold (`tests/test_real_data_invariants.py`). `tests/conftest.py` enforces the network part, and `pytest --fake-now=<ISO time with UTC offset>` (needs `requirements-clock.txt`) freezes the clock to prove the rest; the `fake-clock` job in `checks.yml` does that on every PR.
9. Never edit a pinned total in `tests/test_overrides.py` just to pass. Check each changed game first.

## Invariants (do not break)

Data
- Each school's page is accepted only when its parsed W-L-T, home/away records and current streak equal that page's own summary and no row repeats. Never loosen this, and never check one school's page against the other's. The page's total points/goals/runs is a warning only.
- A page that fails keeps that school's last good games for that sport and the run exits non-zero; everything that passed still updates. A page with fewer games than its saved copy is rejected unless `--allow-shrink`.
- The bot-managed files (`depauw.json`, `wabash.json`, `series.json`, `upcoming.json`, `pending-changes.json`) live on the `data` branch, not on `main`, and are written only by the update workflow (`scraper/databranch.py`). The `data` branch holds nothing else (no code), is never pushed to by hand, never force-pushed, and gets no pull requests. The hand-curated files (`overrides.json`, `alumni.json`, `endowment.json`, `bell-heists.json`, `fun-facts.json`) stay on `main` and change only through pull requests. `python scraper/databranch.py fetch` gets the bot files locally; they are git-ignored on `main`.
- Review hold: a change to a historical game (a season before the sport's current one) is held in `data/pending-changes.json` until a person approves it. Never write such a change straight into `depauw.json` or `wabash.json`. `--allow-shrink` does not lift the hold.
- When the schools disagree, DePauw's version counts and Wabash's is shown beside it. This is a convention, not a finding. Never hide or silently pick a side.
- Prefer a ruling in `data/overrides.json` (with a reason) to changing a merge rule. A ruling that no longer finds its rows fails that sport's merge on purpose. A merge rule change affects every sport: follow README "When you want to change a rule or number".
- `series.json` is always the merge of `depauw.json`, `wabash.json` and `overrides.json`. Do not hand-edit it. Data files are rewritten only when their content changes.
- Parser cases that each broke or nearly broke: half-point scores (`172.5`; a whole score stays an int); a result with no score (`score_known: false`, left out of every score fact); result letter and scores that disagree (trust the letter, swap, `score_order_reversed`); Wabash placeholder dates (Jan 1 to 3) and out-of-season dates (`date_known: false`: never print `date`, never the "most recent" game). These flags are written only when they apply.
- Sources: DePauw's opponent id for Wabash is 215, Wabash's for DePauw is 4. Wabash's slugs differ: men's tennis is `tennis`, swimming and diving is `swimming-and-diving`. `scrape.fetch` stays https-only, same-site and size-capped.
- Politeness (`scraper/politeness.py`): follow each site's robots.txt, read once per host per run before any page; never request a path it disallows for our user agent (that page keeps its last good data and the `report` job names it); keep requests to one host at least its `Crawl-delay` apart (30 s on both schools' sites; 30 s when robots.txt sets none or cannot be read; never under 3 s). Send the one `politeness.USER_AGENT` (site, repository, privacy contact) everywhere the project fetches. Never increase request volume to the schools (more runs, more pages per run, a shorter delay, a new trigger that scrapes) without updating these rules, the README and the tests in the same PR.
- What each run reads (`gameday.plan`): daily and hand-started runs every sport; game-day runs only the sports whose game-day window is open (when none is, those whose game today has started or finished; never a game not yet started); a push to `main` nothing unless it changes a file in `gameday.SCRAPE_ON_PUSH` (the scraper, `sources.json` and `requirements.txt`, so a Python dependency update is tried on the live pages at once). A sport not read keeps its stored games, schedule and pending review entries. "Last checked" on a run that read nothing comes from the Actions cache (the last real scrape) or is left off; it never shows a time when nothing was read.
- Links: `render.safe_url` passes only plain lowercase https links to the two source sites (no backslash, whitespace, quote, login or port); curated data links (`alumni.json`, `endowment.json`, `bell-heists.json`, `fun-facts.json`) must be https; a Wayback link is recorded only if it starts with `https://web.archive.org/web/`. Every spreadsheet cell goes through `csv_text`. `tests/test_hardening.py` pins all of it.
- Scope: men's head-to-head sports only (Wabash is all-male). Swimming and diving counts dual meets only; invitationals, relays and championships never count. Ask the maintainer before adding any other individual or multi-team sport.
- Check values for the current data (update them only when a new result changes them): football merges to 132 games, 60-63-9 (DePauw-Wabash), equal to both pages' own records; the Monon Bell era (1932 season on) is DePauw 44, Wabash 44, 6 ties through 2026, and DePauw has held the Bell since 2022 (5 straight wins); baseball merges to 314 games, 155-156-3, equal to Wabash's page; all sports 919 games, DePauw 542, Wabash 357, 20 ties, 15 disputed scores, none of which changes a winner. `tests/test_overrides.py` pins the per-sport totals of the page fixtures in `tests/fixtures/`, which were captured in October 2026 (football there is still 131 games, 59-63-9); change those pins only when a fixture is refreshed on purpose.

Pipeline
- Every job that reads `data/` runs `databranch.py fetch --remote origin` right after checking out `main` (pull-request checks too, read-only and without a token); `scrape.py --remerge-only` rebuilds `series.json` before the tests (a hard step in `checks.yml`, non-blocking in production). Only the build job's "Commit if data changed" step writes, through `databranch.py push`, to `data` and never to `main`, never with `--force`; a failed push still deploys and turns the run red. `test_data_commit` commits only a marker.
- Tests run before the scrape in `update-and-deploy.yml`. A scraper failure is tolerated (validated fallback data publishes) and the `report` job turns the run red after the deploy. A push made with the workflow's token does not start another run.
- Render is a hard gate: `render.py` runs after the scrape and before the data commit, and a failure stops the build before any commit, upload or deploy. The HTML validation then runs in production in its own `validate` job, which holds no write token and no saved credentials, on the Pages artifact the build uploaded, with the same pinned `setup-node`, locked `html-validate` (`npm ci --ignore-scripts`, run with `npx --no-install`) and ten-page list as `checks.yml`; it, the Node setup, the install and the production script syntax check are non-blocking, and the deploy waits for the build only. The syntax check runs only if Node setup succeeds; pull-request checks remain the hard syntax gate. Never run npm packages, or add steps that fetch code at run time, in the `build` job (it holds `contents: write`). A failed or skipped validation writes a `::warning` annotation and a run-summary note, the site still publishes, and the `report` job turns the run red after the deploy and says which problem it was.
- The frequent cron (`7,37 * * * *`) must equal `gameday.FREQUENT_CRON`; inside a window it stands aside while a game-day watcher runs. GitHub can delay or skip scheduled runs and switches them off after 60 days without repo activity (the daily health check warns from 45 days).
- The game-day watcher (`gameday-watcher.yml`, `scraper/watcher.py`) only reads the `data` branch and dispatches `update-and-deploy.yml` (with `gameday: true`) and relays of itself; it never fetches the schools' sites, commits or deploys. At most one update every `watcher.CADENCE` (15 minutes), final updates included, exactly one final update per game, and one watcher at a time. The one exception is a hand-started test dispatch (`test_dispatch`), which starts a single game-day update and stops; it is never combined with a dry run. Only its `watch` job and the update workflow's `watcher-handoff` job hold `actions: write`; no other job gets it.
- Snapshots: the Wayback calls stay in the last `archive` job, which can never fail the run. A retry merges links and never overwrites them. The limits are the `SAVE_*` constants in `scraper/snapshot.py`.
- `render.py --now` is for previews and tests; no workflow may use it.
- The monthly link check (`link-check.yml`, `scraper/linkcheck.py`) only reads and reports: it never edits the site, the data or the repository, a broken link never fails its run, and only its `issues` job (on `main`) may write, to the one `broken-links` issue. Box-score links on the schools' sites and the pages the scraper already fetches stay excluded, so traffic to the schools' sites stays at the scraper's level. Keep its politeness limits (one request at a time, 2 seconds per host, HEAD first, one retry, one page per link). On the schools' athletics sites it follows the scraper's politeness rules instead of the 2 seconds (the same `scraper/politeness.py`): robots.txt read once per host per run before any page there, requests to that host at least its `Crawl-delay` apart (30 s, with the same fallback and 3 s minimum), and a page robots.txt disallows never requested (counted as skipped).
- The daily health check (`health-check.yml`, `scraper/health.py`) only reads and reports: GitHub's API (GET requests only, never following a redirect, so the token goes nowhere else), the workflow files and one request per run to our own home page, one more if it fails. It never fetches the schools' sites, never commits, pushes or deploys, and never enables, disables or starts a workflow. Nothing in this repository keeps the schedules alive artificially: no enable call on a timer and no empty or keepalive commit, to `main` or to `data`. The answer to GitHub's 60-day rule is the early warning (`health.WARN_AFTER`, 45 days after the last commit on `main`, always below GitHub's 60) and a real merged pull request. Only its `issues` job (on `main`) may write, to the one `site-health` issue, which it assigns to the repository's owner when it opens it (the owner comes from the runner's environment; no account name is written in the code, the workflow or the tests) and in which it never mentions anyone; a problem never fails its run, and a check that could not be made (the home page not loading included) turns the run red without opening or closing the issue, and never counts as a change in the problems.

Site
- No inline JavaScript or styles and no third-party requests. The one currently approved client-side exception is the deferred, same-origin `static/easter-eggs.js` title entrance on `/` and `/alumni/` (on `/` it also shows one random tiger fact per open of the tiger disclosure, from facts already in the page, with no network or storage); it opts into `script-src 'self'` only on those two pages. All eight other generated pages remain script-free under the base CSP (`default-src 'none'`, plus `font-src 'self'` for the one bundled web font, a Latin woff2 subset of Barlow Condensed Bold in `static/fonts/` with its OFL license beside it; the policy string is pinned in `render.CSP`, README and the tests, which change together). Do not add other client-side code without a maintainer decision. No diagrams on the public site.
- The privacy policy (`/privacy/`, `scraper/privacy.py`, linked as "Privacy" from every footer) says the site collects nothing: no cookies, storage, analytics, ads, embeds or third-party requests, and one self-hosted script that makes no network request. Adding a script, analytics, cookies, storage, an embed or any third-party request (including a new host for fonts, images or the domain) means updating the policy text, its `UPDATED` date and `tests/test_privacy.py` in the same PR. Never put anything personal in an issue-form link. Each contact address appears only on its own page: the privacy contact (`privacy.PRIVACY_EMAIL`) only on `/privacy/` and the accessibility contact (`accessibility.ACCESSIBILITY_EMAIL`) only on `/accessibility/`. No other email address is anywhere on the site, and neither is ever in the footer or `security.txt`; `tests/test_privacy.py` pins that.
- Every link within the site reaches a built page or file, and every `#fragment` an existing `id` on its target page; `tests/test_linkcheck.py` builds the whole site and checks (`linkcheck.internal_problems`). Rename an id or a page only together with every link to it.
- Every number on a page comes from the data or a named constant. Never hardcode a count, year or size word ("twice").
- No school logos, wordmarks, seals or official mascot art, on pages or in generated images. The one approved original generic tiger drawing is a small easter egg in `static/easter-tiger.svg`; it is not official mascot art and does not appear in generated images. Keep the site non-commercial (no ads, affiliate links, donations or sales) and not official-looking. Every page keeps the "unofficial fan site, not affiliated" note.
- Text rules: curly apostrophe (’) in visible text, serial comma in lists of three or more, AP-style locations (display only), dates like "Oct 29, 2026". Each page's footer comes from `site_footer()`; add footer content as a block there, never as page HTML. Each page's header comes from `site_header()` (skip link first, one `<main id="main">`, nav links at least 44 px tall); never build a header inline. Every record bar (home page, sport cards, alumni page) uses only the `.w-0` to `.w-100` width classes (never inline styles) with widths from `bars.record_widths`, which sum to 100. The every-game chart on each card is build-time inline SVG from `scraper/chart.py` (no JavaScript; the bar width is a `stroke-width` attribute, not a `style` attribute). Colors come from the tokens at the top of `static/styles.css` (text roles at least 4.5:1, fills at least 3:1, in light and dark; `tests/test_shell.py` and `tests/test_accessibility.py` check it); gold as text is `--color-depauw-text`, never the fill.
- Game lists (`render.games_table`): each card's games sit in one native `<details>` per decade (`facts.by_decade`, by the game's date; the newest decade open, the rest closed, games with no recorded date in a last, closed "Date not recorded" group), every summary computed from that group's own games, and no script. The phone layout (two lines per game, up to `42rem` wide) is CSS only on the same table: never remove the header row or a cell for it (clip it, never `display: none`), keep the result letter as text in every row, and change the column order in `render.GAME_COLUMNS` only together with the `nth-child` rules in `static/styles.css`. Nothing links into a game list, and nothing inside one has an `id`: add neither without a maintainer decision. (A closed decade hides its rows; current browser engines open it themselves for a link to a row inside it, as measured in Chrome, Firefox and WebKit in November 2026, but older browsers were not tested.) `tests/test_game_list.py` checks all of it.
- `data/fun-facts.json` (the tiger easter egg) is hand-curated like the alumni data: validated on every build by `scraper/funfacts.py`, changed only through PRs, every fact in our own words with an opened source link, the DePauw and Wabash counts within one of each other, nothing the athletics data already shows, never touched by the scrape. Without JavaScript the visible fact comes from the Eastern date, never `random()` in the build. A fact says when with a date or a year: the validation refuses the whole words "currently", "today", "now", "this year" and "this season" (`funfacts.STALE_WORDS`). The Bell's weight and the tie rule (told as history, before overtime came in 1996) appear both in the home page's Monon Bell block (`render.BELL_HISTORY`) and in the facts `both-bell-weight` and `both-tie-rule`; `tests/test_tiger_facts.py` fails unless they agree, so change them together.
- `data/bell-heists.json` (the heist history page) is hand-curated like the alumni data: validated on every build, changed only through PRs, every story sourced with a link that has been opened, written in our own words, and never touched by the scrape. Every story carries a `rating` (`documented`, `reported`, `lore` or `disputed`) that says how well it is sourced, and a part of a story that is lore says so in its own text. Wikipedia and fan pages are leads only, never a story's source; a link to an Internet Archive copy is labelled "(archived copy)". Do not name a student in an incident after about 1980, or anyone connected to criminal charges, even when a source does. A story's optional `tactics` (keys from `heists.TACTICS`) and `lesson` feed the fictional `/bell-heist/` page: tag a story only when its sourced text clearly shows the tactic.
- The joke page (`/bell-heist/`) stays satire with a plain "please don't": its two data sections ("Lessons from the archive", "The odds") are worked out from `data/bell-heists.json` at build time, with no number or outcome typed into the page, and they describe outcomes only, never ways around current security. No detail about sensors, alarms, guard schedules, building access, where the Bell is kept now or what "would have worked"; if a line could read as advice, cut it. The page keeps the joke's text, both of its links, the base CSP and no script; `tests/test_bell_lessons.py` checks all of it.
- Accessibility: the site aims to meet WCAG 2.2 level AA, and `/accessibility/` (`scraper/accessibility.py`, linked as "Accessibility" after "Privacy" in every footer) says what was tested, what was not and what is known not to work. Keep all four of these: contrast (4.5:1 for text, 3:1 for fills, edges and focus rings, in light and dark), keyboard access (everything reachable and usable, a visible focus ring, the skip link first, no positive `tabindex`, never `outline: none`), reduced-motion support (any animation or transition is off under `prefers-reduced-motion`) and text alternatives (alt text or a name for every image, chart, link and button; an accessible name starts with the visible text; no meaning by color alone). The contrast test in `tests/test_accessibility.py` must pass: set colors only through the `--color-*` tokens, list every new token in that test with the surfaces it is drawn on, and fix a failing pair by changing the token, never by loosening the threshold or the list. The page says "aims to meet", never "conforms" or "certified". A fix, a new limitation, a new round of testing or a change that makes a statement on the page untrue updates the page text and its `UPDATED` date in the same PR (as the privacy policy does).
- Alumni and endowment data is hand-curated, validated on every build and reviewed in PRs. No overall alumni score. Endowment per student uses one basis (pooled endowment net assets) and the 5% "about even" rule. Do not return to the unadjusted totals without a maintainer decision.

## Repo hygiene

- Commit only the project's own files. No plans, working notes, credentials, personal details or local file paths. Do not add files that are not part of the project unless the maintainer asks. `docs/` holds one older plan; do not add to it.
- Pin every GitHub Action to a full commit SHA with a version comment, or the workflow fails.
- The deploy uploads dot files (`include-hidden-files: true`), so the only dot entries the built site may hold are `.nojekyll` and `.well-known/security.txt` (`tests/test_security_contact.py`). The security contact is GitHub private vulnerability reporting, never an email address; keep `SECURITY.md` and `security.txt` in step.
- Every job runs on one pinned runner image (`runs-on: ubuntu-24.04`, never `ubuntu-latest`), so GitHub's image rollouts cannot change a run by themselves. Change all `runs-on:` lines together, deliberately, after trying the new image on a pull request; `tests/test_runner_image.py` checks this.
- npm packages are locked too (`package.json` with an exact version, `package-lock.json`): install with `npm ci --ignore-scripts`, run with `npx --no-install`, never `npx --yes` for the validator. The accessibility check's tools (`axe-core` and `playwright-core`) are locked in their own folder, `axe/`, by the same rules, so the root lock that production installs never changes with them; only the read-only `axe` job in `checks.yml` installs or runs them, with the Chrome already on the runner, and it is not a required check for now. `tests/test_npm_lock.py` checks this.
- Python packages are locked. Change `requirements.in` or `requirements-clock.in`, regenerate the matching `.txt` with `pip-compile --generate-hashes` on Python 3.12 (the version the workflows use), and keep every workflow installing with `--require-hashes -r requirements.txt`. Never install from the `.in` files in a workflow or loosen the pins; `tests/test_requirements.py` checks this. README "Dependencies" has the detail.
- Workflows use `pull_request`, never `pull_request_target`, request the minimum permissions per job and use no secrets.
- Tests that run the committed rulings against `tests/fixtures/` fail if a fixture is refreshed with changed rows. Refresh them together with the rulings.

## Collaboration

- Branch from the latest `main`. Any descriptive name works (`feat/…`, `fix/…`, `docs/…`, `codex/…`).
- `main` moves (others merge; the data bot commits to the `data` branch, not to `main`). Before pushing, `git fetch origin` and bring the branch up to date: rebase if it was never pushed, merge `origin/main` if it was. Keep both sides' changes, then re-run the checks. The "Protect main" ruleset requires an up-to-date branch.
- One PR per change. Never push to `main`. Never force-push a shared branch.
- The required status check is the `checks` job in `checks.yml` (matched by job name, not file name). Renaming the job needs a matching ruleset change by the maintainer.
- The maintainer reviews and merges. Pull requests from forks need approval before workflows run.
